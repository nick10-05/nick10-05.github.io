(The problem)

Webhooks fail quietly. A provider sends an event, your server crashes for thirty seconds, and that payment confirmation is simply gone — with no record it ever arrived.

RelayForge sits in between: it stores every event before acknowledging it, then delivers it to one or many destinations until it lands.

(How it works)

PostgreSQL is the job queue. A transactional outbox records each event; workers claim jobs with SKIP LOCKED, hold them on a lease, and retry with backoff. Anything that keeps failing moves to a dead-letter state you can replay.

If a worker dies, its lease expires and another picks the job up. Fenced writes mean a stale worker can never overwrite a newer result — the guarantee is at-least-once delivery.

(Security)

An SSRF-safe HTTP client so destinations can't point at internal networks, HMAC-signed deliveries with key rotation, and destination secrets encrypted with AES-256-GCM.

(Proof)

560 CI tests run against a real PostgreSQL. In local k6 load tests it ingested 665 requests per second — and after killing the server mid-run, all 38,260 events were still delivered.

Every major decision is written up as one of 5 architecture decision records in the repo.
